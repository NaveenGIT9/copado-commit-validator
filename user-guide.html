Copado Commit Validator — User Guide

A plain-English reference for every term, badge, status, and checkbox you see in the tool. Use the sidebar or search to jump to what you need.

What is this tool?

The Copado Commit Validator is a VSCode extension that helps you check whether your Salesforce User Stories are ready to promote through the Copado pipeline — before you actually promote them.

It does three things:

  1. Reads your Copado org to understand each story's commits, tests, approvals, and last promotion state.
  2. Compares those against the actual Git branch to catch commits that Copado doesn't know about yet.
  3. Shows you a table of results, flags problems, and lets you create promotions directly from the UI.
Think of it as a pre-flight checklist — it tells you what would block a promotion before Copado even tries.

How to use it

  1. Open the extension panel in VSCode.
  2. Enter your story names (one per line or comma-separated) in the text box.
  3. Select your Org Alias (the Copado org to query) and your local Git Repo Path.
  4. Click Verify. The tool fetches data and builds the results table.
  5. Review each story's verdict and eligibility status.
  6. Check/uncheck the stories you want to promote, then click Promote Eligible Stories.
The tool also has a Fetch Ready mode that auto-loads all stories from a QA or UAT list view — so you don't need to type story names manually.

User Story

A User Story (e.g. US-0024914) is a Copado record that represents a unit of work — a feature, bug fix, or configuration change. It has:

  • A dedicated Git feature branch (feature/US-0024914)
  • A source environment (the sandbox where development happened)
  • Registered commits, metadata components, and optionally tests and deployment tasks

Promotion

A Promotion (e.g. P27860) is a Copado record that groups one or more User Stories together and moves them from one environment to the next in the pipeline.

When you click Promote in this tool, it:

  1. Creates a new copado__Promotion__c record in Salesforce.
  2. Links your selected stories to it.
  3. Optionally triggers Merge & Deploy in Copado automatically.
TermMeaning
Merge & DeployCopado merges the story branches into the target environment branch AND deploys the metadata to the target org.
Deploy ChangesSkip the merge step — only deploy metadata. Used when the merge was already done manually.
Re-triggerRun Merge & Deploy again on an existing promotion (no new record created). Used after resolving conflicts.

Pipeline & Environments

A Pipeline defines the promotion path: DEV → QA → UAT → PROD. Each step is an Environment.

In the results table you will see a column like RBKDEV1 → RBKQA — this is the story's source environment → destination environment. The tool auto-detects this from the story's assigned org and the pipeline configuration.

Pipeline level: internally the tool assigns a numeric level to each environment (0 = DEV, higher = closer to PROD). This is used to determine whether a parent story is "ahead" of a child story.

Registered vs Unregistered Commits

Every time a developer commits code via Copado's "Commit Changes" UI, Copado creates a copado__User_Story_Commit__c record. These are registered commits — Copado knows about them.

Unregistered commits are commits on the feature branch in Git that Copado has no record of. They may have been:

  • Committed directly via Git (bypassing Copado's UI)
  • Auto-generated by tooling (e.g. source API version bumps)
  • Amended/rebased commits that Copado's SHA no longer matches
Unregistered commits don't always block promotion — the tool checks whether they only touch components already declared in the story's metadata list. See the Covered verdict below.

Copado Auto-commits

Some commits are made automatically by Copado pipelines — for example, bumping sourceApiVersion or clearing PMD rulesets. The tool detects these by their commit message prefix and always exempts them — they never block promotion.

Base Branch / Parent Story

A story's Base Branch (copado__Base_Branch__c) tells Copado which branch to diff against. If it points to another story's feature branch (e.g. feature/US-0004674), that story is the Parent Story.

The tool detects this and checks whether the parent story is already in a higher environment than the child. If not:

Parent Story Not Promoted — the child story will be blocked. The parent must be promoted first.

Deployment Tasks

Deployment Tasks (also called Job Steps — copado__JobStep__c) are manual tasks, data sets, or scripts attached to a story that run as part of deployment. Examples: insert a Custom Metadata record, run a data migration script.

If a story has no commits but has deployment tasks, it is still considered promotable. If it has neither commits nor deployment tasks, the tool flags it as No Commits and excludes it.

PR Approval

Pull Request Approval — the field copado__Pull_Requests_Approved__c on the User Story. When checked in Copado, it means a senior developer or reviewer has approved the code changes in GitHub.

If this is false and the story has commits, the tool blocks promotion with a "PR not approved" warning. Stories with no commits are exempt from this check.

✓ Clean

✓ Clean

Every commit on the feature branch is registered in Copado. There are no extra commits. This is the ideal state — the story is ready to promote from a commit standpoint.

Covered (same author)

✓ Covered — same author

There are unregistered commits, but:

  • All the files they touch are already declared in the story's Copado metadata list, AND
  • The author of those commits matches the author of the registered commits.

This usually means the developer forgot to click "Commit" in Copado but the code is effectively the same scope. The tool treats this as safe to promote.

Needs Verify

⚠ Needs Verify

Unregistered commits exist, all their components are covered in the metadata list, but the author is different from the story's registered commit author. This could mean:

  • A second developer pushed changes to this branch.
  • A commit was amended and the committer email changed.

The tool flags this for human review — a DevOps admin should confirm the changes are intentional before promoting.

Unregistered Commits

✗ Unregistered Commits

Unregistered commits exist AND at least one of them touches a component that is not declared in the story's Copado metadata list. This means Copado won't deploy those components — they'll silently be missing from the promotion.

The developer must go back to Copado, register those commits, and add the missing components to the story's metadata before this story can promote.

Also shown when a commit has a Copado status of "Commit not in branch" or any non-Failed, non-Complete status — these always block regardless of coverage.

No Commits

— No Commits

The story's feature branch exists but has no commits ahead of the base branch, and Copado has no registered commits for this story. This can mean:

  • Development hasn't started yet.
  • The branch was created but never committed to.
  • The story only has Deployment Tasks (no metadata changes) — in that case it's still eligible.

Stories with truly no commits AND no deployment tasks are excluded from promotion.

In Progress / In Queue

⏳ In Progress — P27860

A Copado Job Execution (JE) for this promotion is currently running or queued. This is the authoritative check — the tool looks at the actual Job Execution status, not just the promotion record's status field.

  • In Queue — Copado has accepted the request and is waiting to start.
  • In Progress — Merge & Deploy is actively running.

If the job has been running for 45+ minutes, the badge turns red and shows "possibly stuck" — this usually means the Copado job hung and may need to be cancelled manually.

While a job is running, the story is not eligible for a new promotion.

Merge Conflict

⚠ Merge Conflict — P27860

Copado attempted to merge the story's branch into the target environment branch and found conflicting changes. The promotion is stuck until the conflict is resolved manually.

Culprit story (the one that caused it)

The tool parses the Copado Job Execution error message to identify which story's branch caused the conflict. That story shows the red ⚠ Merge Conflict badge and is Not Eligible for a new promotion until the conflict is resolved.

Innocent story (the others in the same promotion)

ℹ Not yet merged in P27860 — conflict caused by US-XXXXX

Other stories in the same promotion that didn't cause the conflict are called Innocent. They are still eligible but should be promoted separately (in their own new promotion) so they don't get stuck waiting for the conflict to be resolved.

The tool automatically checks the merge order to tell you whether an innocent story:

  • Was already merged into the promotion before the conflict happened (safe to separate), or
  • Had not been merged yet when the conflict occurred.

Conflicts Resolved

⚠ Conflicts resolved — re-initiate promotion

A developer has manually resolved the merge conflict on the promotion branch in Git and the promotion status was updated to Conflicts Resolved. The promotion is ready to be re-triggered — Copado can now complete the merge.

Single-story Conflicts Resolved

The promotion only contained one story. The tool marks the story as eligible and will re-trigger the same existing promotion when you click Promote.

Multi-story Conflicts Resolved

Multiple stories were in the promotion. The tool shows a special checkbox in the Separate Promo column:

  • Unchecked (default) — re-trigger the same existing promotion for all sibling stories together.
  • Checked — create a brand new separate promotion for just this story.

See Resolution Attachments for what the label under this checkbox means.

Completed with Errors

✗ Failed — no fix commit

The promotion ran but Copado reported deployment errors (Apex test failures, missing dependencies, etc.). The promotion status is Completed with errors.

If the story is solo in that promotion and no new fix commit has been made since the failure, the tool flags it as not auto-eligible. The developer needs to fix the issue and commit again — then the tool will pick up the fix and the story becomes eligible.

If the story was in a multi-story promotion when it failed, the tool can't attribute the failure to one specific story — so all stories in a multi-story failed promotion are still treated as eligible.

Validation Failed

✗ Validation failed — no fix commit

Same as Completed with errors but specifically for a validation-only deployment run. The Apex tests or metadata validation failed. A fix commit is required before the story can be promoted again.

Validated

⚠ Validated only — not deployed

The promotion ran a validation (dry-run check) successfully — metadata and tests passed — but the changes were not actually deployed to the target org. This is a common two-step deployment approach.

When you promote a Validated story, the tool skips the merge step and only triggers Deploy Changes to complete the deployment using Copado's quick-deploy mechanism.

Stale Promotion

✓ Fix committed after last Completed with errors

A promotion shows a warning status (e.g. Completed with errors, Merge Conflict) but a newer commit was registered after that promotion was last modified. This means the developer has already addressed the issue.

The tool ignores the old promotion warning and treats the story as if it has no warning — i.e., the story becomes normally eligible. The "stale promo" info row in the table confirms what the old promotion's status was and that it's been superseded.

Staleness check: the tool compares copado__Latest_Commit_Date__c (and the latest unregistered commit date from Git) against the promotion's LastModifiedDate. If any commit is newer → the promotion is stale.

Promotable? column

This column summarises whether the story is ready to promote. The result is a combination of all the checks below:

What makes a story eligible (✓ Yes)
  • Commit verdict is Clean, Covered, or No Commits + has deployment tasks
  • No failed Apex tests linked to the story
  • PR is approved (or story has no commits)
  • Apex test class is linked (if story has Apex code)
  • No parent story blocking it
  • No dependency blocking it (all parent stories are ahead)
  • Last promotion is not in a warning state — OR it's Conflicts Resolved / Innocent conflict
Blockers shown in this column
BlockerWhat it means
PR not approvedThe Pull Requests Approved checkbox on the story is unchecked.
No Apex test linkedStory has Apex classes but no test record in Copado.
Parent story not promotedThis story's Base Branch points to another story that hasn't been promoted yet.
Dependency not aheadA story this one depends on (via copado__Team_Dependency__c) is still in the same or lower environment.
No commits, no tasksStory has nothing to deploy — no registered commits and no deployment tasks.
In ProgressA Copado job is currently running for this story's promotion.
Merge Conflict (culprit)This story's branch is causing a conflict in an active promotion.

Force Promote

The Force checkbox appears next to stories that are technically eligible (clean commits, tests passing) but have a blocking condition that the tool cannot automatically resolve:

  • Last promotion failed with no fix commit — the developer hasn't pushed a fix yet, but you want to retry anyway.
  • Dependency not ahead — a parent story hasn't been promoted yet, but you know it's safe to proceed.
Force promoting ignores safety checks. Use with caution — if the underlying issue isn't actually resolved, the promotion will likely fail again in Copado.

When force stories are in the list, a Re-Verify Force Stories button appears — click it to re-check just those stories to see if the developer has committed a fix since the last verify run.

Separate Promo checkbox

When checked, this story will be placed in its own new promotion instead of being grouped with other stories from the same project and environment.

When does this checkbox appear?

ScenarioDefault stateWhat happens
Normal eligible story Unchecked Grouped with other stories from the same project + environment into one promotion
Innocent Merge Conflict story Unchecked (you decide) Always creates a separate promotion for this story regardless
Conflicts Resolved (multi-story) Unchecked Unchecked = re-trigger old promotion. Checked = new separate promotion + copy resolution attachments

Skip checkbox

The Skip checkbox (shown in the promote summary panel) lets you exclude a specific story from the current promote run, even if it's eligible. Useful when:

  • You're promoting a batch but one story needs to wait.
  • You want to promote stories individually to control order.

Skipped stories stay visible in the promote summary with a strikethrough — they're not removed, just excluded from the current batch.

Resolution Attachments

When a developer resolves a merge conflict in Copado, Copado stores the resolved file content as Attachment records on the Promotion object. These are named RESOLVED <StoryName> <filepath>.

When you promote a Conflicts Resolved multi-story and check Separate Promo, the tool can copy these resolution attachments from the old promotion to the new one — so Copado knows not to re-prompt the developer to resolve the same conflict again.

The label under the Separate Promo checkbox

[resolution attachments will be copied for this US if any]
The latest commit on the story is older than when the conflict was resolved. The resolutions still apply to the current code — they will be copied to the new promotion automatically.
[resolutions stale — not copied]
The developer committed new code after the conflict was resolved. The RESOLVED files no longer match the current branch state — copying them would cause incorrect resolutions. The tool skips the copy; the developer may need to re-resolve.
Staleness check: the tool uses the later of the Copado-registered latest commit date and the latest unregistered Git commit date — so even commits that Copado missed are counted.

Story Dependencies

Dependencies are defined via Copado's copado__Team_Dependency__c object. They tell the pipeline that Story A depends on Story B — meaning Story B must be promoted first.

The tool checks all dependencies where the current story is the child/dependent. For each dependency, it determines:

FlagMeaning
Parent Ahead The parent story is in a higher pipeline environment than the child — it's already been promoted past the child's current stage. Safe to proceed.
Parent In Same Promo The parent story is in the same current promotion as the child — they're being promoted together. Treated as safe (not a blocker).
Blocked Parent is in the same or lower environment and not in the same promotion. The child story is blocked until the parent is promoted.

Re-trigger

Re-triggering means running Copado's Merge & Deploy on an existing promotion record — no new promotion is created.

This is used when:

  • A Conflicts Resolved promotion needs to be re-run after the conflict was fixed.
  • A Validated promotion needs to be deployed (quick-deploy).

When you leave the Separate Promo checkbox unchecked for a Conflicts Resolved story, the tool re-triggers the same old promotion. If you check it, a brand-new promotion is created instead.

Re-triggering is faster than creating a new promotion — it skips the create + link steps and goes straight to Merge & Deploy.
