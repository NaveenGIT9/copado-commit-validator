What it does

The gap between committing and actually deploying

When a developer commits in Copado, two things are supposed to happen together — the files land in git and Copado registers those files against the User Story. If both happen correctly, the deployment works. If they get out of sync, Copado will silently skip those files at deploy time — and the developer's changes never reach the target org.

This tool runs a check before any promotion starts. Here's exactly what it does:

How the validator works
1
It counts how many commits are on the feature branch in git — say a developer made 5 commits.
2
It counts how many of those commits are registered in Copado against the User Story with a status of "Complete".
3
If the numbers don't match, there are unregistered commits — commits sitting in git that Copado has no record of.
4
For every commit on the branch — registered or not — it checks: are the metadata components in that commit listed on the User Story? If any component is in git but not on the story's component list, Copado will skip it at deployment. The file stays in git but never reaches the target org.
Why this matters: Copado doesn't deploy everything in git. It only deploys components that are registered on the User Story. Think of it like a shopping list — Copado only buys what's on the list. If your Apex class is in any commit on the branch but isn't on the story's component list, it gets left behind every single deployment — whether that commit was registered or not. The developer eventually comes to the DevOps team saying "my changes didn't deploy" — and that's exactly what this tool prevents.

What it catches

Three things that silently break Copado deployments

Each of these happens without any obvious error in Copado's UI. By the time someone notices, the deployment has already failed — or the wrong changes already reached production.

Issue 1
Commits in git that Copado won't deploy

This is the most common and most confusing one. A developer commits 5 times on their feature branch. But Copado only has 3 of those registered as "Complete" on the User Story. The other 2 are unregistered — they're in git, but Copado has no record of them.

5 commits in git 3 registered in Copado 2 unregistered

The validator then goes through every commit on the branch — registered and unregistered — and checks each metadata component inside them against the User Story's component list. It's not just the unregistered commits that matter. Even a registered commit can carry a component that isn't properly on the story's list. If an Apex class is in any commit on the branch but not on the story's component list, Copado will skip it during deployment. The class changes stay in git forever but never reach the target org.

What the developer sees They push the promotion, it completes with no errors, they go to the target org — their changes aren't there. They come to the DevOps team saying "my changes didn't deploy." The validator catches this before promotion starts.
Issue 2
Child story tries to promote before the parent has gone first

In Copado, stories can have a parent-child dependency. The rule is simple: the parent must reach the target environment before the child can follow. If the child promotes first, things break in the target org.

The validator checks where the parent story currently sits and tells you whether the child is safe to promote:

Parent is ahead of the child — for example, parent is already in QA and child is still in DEV. The dependency is satisfied. Child is promotable.

Parent is in the same environment as the child — parent hasn't moved forward yet. Child is not promotable. You'll see this flagged clearly. There is a force-promote option, but it should be a conscious decision, not an accident.

This check covers both ways the parent-child relationship can exist in your setup:

1. Copado User Story Dependency — the parent is officially configured in Copado's dependency setup for that child story.

2. Base branch relationship — the child story's feature branch was created off the parent's feature branch (not off main or org branch). The child's git history already includes the parent's changes, so the parent still needs to go first for the deployment to land correctly.

What this looks like without the check A developer promotes their child story to QA. The parent is still sitting in DEV. QA gets the child's changes without the parent's foundation — the feature is broken, and it takes the team time to figure out why something that "worked in DEV" is failing in QA.
Issue 3
A hidden git merge that silently ships unrelated stories to QA

This one is subtle and easy to miss. A developer runs into merge conflicts while working. Instead of resolving conflicts through Copado the right way, they go directly into git and fix them manually. In doing so, they accidentally merge the target org branch (e.g. INT) into their own feature branch.

Here's why nobody catches it:

The PR looks clean. The developer raises a PR against the INT target branch as normal. The reviewer sees no unexpected changes in the diff — because the INT branch is already the target, so those changes don't show up as new. The reviewer approves. It deploys to INT fine.

The damage happens on the next promotion. When this story promotes beyond INT — to QA — its feature branch is now carrying INT's entire branch history inside it. That means every story sitting in INT that was never meant to go to QA yet gets pushed to QA through this developer's feature branch. Those stories deploy before they were supposed to, without any approval, without anyone realising it happened.

Why it's impossible to catch manually You can't review every single commit in every feature branch before deployment. The PR diff shows nothing wrong. The only way to detect it is to specifically check whether the target org branch has been merged into the feature branch — which is exactly what the validator does.
What's in the panel

Everything you need before you hit Promote

Enter your User Story IDs and your org alias. The extension pulls the data and lays it out in one place.

Commit Count Comparison

Shows commits on the branch vs. Copado's "Complete" commit records. Any gap means there are unregistered commits the validator then checks further.

Component Coverage Check

For every commit on the branch — registered or not — identifies each metadata component and cross-checks it against the User Story's component list. Flags any component that's in git but missing from the list.

Story Metadata Summary

Lists every component registered on the User Story — type, API name, status — so you can see the full scope of what Copado will actually deploy.

Parent Story Guard

Checks parent-child dependencies — both Copado's official dependency config and base-branch relationships — and tells you whether the child story is promotable or blocked until the parent moves ahead.

Org Branch Merge Detection

Detects if the target org branch (e.g. INT) has been merged into the feature branch — the hidden contamination that silently carries unrelated stories to QA through someone else's promotion.

Last Promotion Status

Shows when the last promotion ran and whether it succeeded or failed — right in the panel, without opening Copado in the browser.

Promote from VSCode

Once the checks pass, trigger the Copado promotion directly from the panel. Status updates stream back in real time — no browser tab needed.

Direct Copado Links

Every User Story ID is a clickable link. Opens the Copado record directly — useful when you need to review the full commit log or deployment history.

When to use it

Run it before every promotion

The check takes under two minutes. That's a lot cheaper than diagnosing a failed deployment after it reaches UAT or production.

  • Before any promotion — confirm that every commit on the branch has a matching Copado commit record, and that every metadata component in those commits is registered on the User Story's component list.
  • When promoting a child story — verify the parent dependency is satisfied. The validator tells you whether the parent story is ahead of the child (promotable) or still in the same environment (blocked), covering both Copado dependency config and base-branch relationships.
  • When you suspect branch contamination — check whether the target org branch (e.g. INT) was accidentally merged into the feature branch by a developer resolving git conflicts outside of Copado.
  • When the last promotion failed — the validator shows when the failure happened and whether the developer made any new commit on the feature branch after that failure. If they did, it signals that a fix was applied since the last attempt and you can proceed with confidence.
