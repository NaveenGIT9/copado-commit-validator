Commit Intelligence

Surfaces every unregistered commit on a feature branch — automatically, with full metadata analysis

What It Detects

  • Compares all commits on origin/master..feature/US-XXXXX against the SHA list registered in Copado — every gap is surfaced.
  • For each unregistered commit: which metadata components it touches, whether those components are inside the story's declared scope, and who authored it.
  • Amended commit detection — when author email ≠ committer email, the commit is flagged ✎ amended — a common sign of a peer modifying someone else's commit.
  • Auto-commit exemption — Copado-generated commits (sourceApiVersion bumps, PMD rule list updates) are identified by their commit message prefix and excluded from all checks so they never block a promotion.
How the stale-resolution date works with unregistered commits

For Conflicts Resolved stories, the tool needs to know if any new developer work happened after the conflict was resolved. copado__Latest_Commit_Date__c only reflects Copado-registered commits and can be outdated. So the tool also extracts the committer timestamp (%cI) from each unregistered commit and takes the latest across all of them as latestUnregisteredCommitDate. The effective date used for the stale check is max(copado_date, latestUnregisteredCommitDate).

Verdict System

  • ✓ Clean  All commits on the branch are registered in Copado. No unregistered work. Eligible to promote.
  • ✓ Covered  Unregistered commits exist but every metadata component they touch is inside the story's declared scope and the committer is the same developer. Still eligible to promote.
  • ⚠ Needs Verify  Metadata scope matches, but the commit was authored by a different developer — could be a peer fix or an unauthorized change. Manual review required before promoting.
  • ✗ Unregistered  Commits touch metadata components outside the story's declared scope. These must be registered in Copado first — story is blocked.
  • — No Commits  Feature branch has no commits ahead of master. Eligible only if the story has deployment tasks (Data Set, Manual Task, etc.); otherwise blocked.

StorySituationVerdict

Quality Gates

Every gate must pass for a story to be marked Promotable. All checks run in parallel.

PR Approval

  • Read from copado__Pull_Requests_Approved__c on the User Story record — a Copado-managed boolean.
  • If the story has metadata (at least one component in its scope) and PR is not approved → blocked. No metadata = no PR gate.
  • Stories on a no-commits verdict bypass the PR gate — there is no code to review.

Test Results

  • Fetched from copado__Test__c — each record has a tool type (Apex Tests, PMD, sfdx-scanner) and a status (Passed / Failed / Not Started).
  • Tool label falls back intelligently: tool → type → name so even records with null fields display the right label (e.g. "PMD - US-0004675" → "PMD").
  • Any test in Failed or Error status → story is blocked from promotion.

Parent Story Dependency

  • Reads copado__Base_Branch__c on the User Story. If it points to another story's feature branch (e.g. feature/US-0004674), that parent story must already be in a higher environment.
  • Uses the pipeline's credential order (credLevel map) to determine "higher." If the parent is on the same credential or the pipeline order is unknown, the tool makes a safe assumption rather than falsely blocking.
  • Parent story not yet promoted → child story shows Parent not promoted and is blocked.

Promotable Decision — All Gates

A story is Promotable only when ALL of the following are true

✓ Commit verdict is acceptable Clean, Covered, or No-commits-with-tasks
✓ Zero failed tests All test records pass
✓ PR approved (or no metadata) copado__Pull_Requests_Approved__c
✓ Parent story already promoted Or no parent dependency

Promotion Safety — Last Promotion Warning

Detects when the previous promotion is in a warning state and blocks re-promotion until it is safe

Warning States Detected

  • Completed with Errors — the last promotion failed. Story is blocked. The developer must push a fix commit (registered in Copado) after the failure date — then the tool clears the warning automatically on the next verify run.
  • In Progress — a promotion is actively running. Blocked to prevent double-promoting. Includes the case where Copado's promotion status stays "Draft" but an SFDX Promote / Deploy job execution is actively running — the tool detects this secondary state too.
  • Stuck Detection — when a promotion has been "In Progress" for more than 60 minutes, the spinner badge changes to Stuck? so the release engineer knows to investigate in Copado.
  • Merge Conflict — the last promotion failed due to a git merge conflict. Handled in detail in Section 4.
  • Conflicts Resolved — Copado created a special re-trigger promotion after conflicts were manually resolved. Handled in detail in Section 5.
How "Completed with Errors" auto-clears
  • On verify, the tool reads copado__Latest_Commit_Date__c from the User Story
  • If that date is after the failed promotion's LastModifiedDate, the warning is considered resolved — the developer has pushed a fix since the failure
  • If no new commit exists → story stays blocked — developer must commit the fix first

Environment & Pipeline Display

  • Each story row shows its Source → Target pipeline step (e.g. TRNDEV1 → TRNQA) so the release engineer always knows which step a story is on — no need to open Copado.
  • Lookup is name-based (not ID-based) to handle Copado's pattern of having different Org__c records for the same environment — far more reliable in practice.
  • All environment names are normalized to lowercase internally for case-insensitive pipeline matching, then displayed in uppercase in the UI — handles Copado orgs stored as "TRNDEV1" and pipeline steps stored as "trndev1" without any manual config.

Merge Conflict — Culprit vs Innocent

Not every story in a conflicted promotion is at fault — the tool tells them apart

How Culprit Is Identified

  • When a promotion has status "Merge Conflict," the tool queries the linked copado__JobExecution__c error message and applies a regex to extract which branch caused the conflict.
  • Culprit story — the one whose feature branch introduced the conflicting change. Marked ⚠ Merge Conflict. Blocked — developer must fix and re-promote.
  • Innocent stories — all other stories in the same promotion. They did nothing wrong. Marked Not yet merged — conflict caused by US-XXX and shown a Separate Promo checkbox pre-checked — they can promote independently right now.
  • Culprit-in-list note — if the culprit story is also in the current verify run, the innocent badge is updated to say "(also in this list — not eligible)" so the release engineer has full context without switching views.
Innocent stories bypass the "last promo warning" gate

Normally a story with a non-null lastPromoWarning is excluded from cleanStories (not eligible to promote). Innocent conflict stories are an explicit exception — isInnocentConflict = true bypasses this gate and they appear in cleanStories with separate: true (forced separate promo).

Conflicts Resolved — Smart Re-trigger

When Copado creates a Conflicts Resolved promotion, the tool decides the safest promotion path automatically

Two Promotion Paths

  • Path A — Re-trigger together (Separate Promo checkbox unchecked): All sibling stories from the original promotion are in the current verify list and eligible. Safest path — re-uses the existing Conflicts Resolved promotion ID. No new promotion record created.
  • Path B — Separate promotion (Separate Promo checkbox checked): One or more siblings are missing from the verify list or are ineligible. This story promotes on its own in a new promotion. The tool automatically copies RESOLVED attachments from the old promotion to the new one.
What are RESOLVED attachments?

When a developer manually resolves a git merge conflict in Copado, the resolution is stored as an Attachment record named RESOLVED <StoryName> <filepath> on the promotion. When a new promotion is created separately, Copado won't automatically know about these past resolutions. The tool copies them to the new promotion so Copado can skip re-resolution for files that were already resolved — avoiding repeated manual conflict work.

Stale Resolution Guard

  • Resolutions are only copied when they are still valid — i.e. the developer has not pushed new code since the conflict was resolved.
  • The guard uses: effectiveLcd = max(copado__Latest_Commit_Date__c, latestUnregisteredCommitDate)
  • If effectiveLcd < Promotion.LastModifiedDate → resolutions are valid → will be copied
  • If effectiveLcd ≥ Promotion.LastModifiedDate → new code was pushed after resolution → resolutions stale — not copied — Copado will re-resolve fresh.
  • Why two dates? Copado's registered commit date can lag — if a developer pushed to git but didn't register the commit through Copado, copado__Latest_Commit_Date__c would be outdated. The tool independently reads committer timestamps from each unregistered commit (via git) and takes the max, ensuring no new developer work is missed.

Sibling Story Eligibility — How It Is Determined

What is a sibling story?

All user stories that were part of the original promotion that entered Conflicts Resolved status. Fetched from copado__Promoted_User_Story__c for that promotion ID, including the credential (environment) each story is currently on.

1
Fetch all sibling story names and their credentials from the original promotion.
2
Compare against verifiedStoryNames (what's in the current verify run) and eligibleStoryNames (what's in cleanStories — all promotable stories across any CR group).
3
Classify each sibling: Missing from current list if not verified at all, Not eligible to promote if verified but blocked.
4
Show warnings grouped, with credential next to each name:

Promote Workflow — From Verify to Copado Promotion

One-click promote with intelligent grouping, override controls, and full audit trail

Grouping Logic

  • Stories are grouped by Project ID + Source Credential ID. Stories on the same project and pipeline step go into one promotion — no manual effort, no cross-environment mixing.
  • Different source credentials → automatically separate promotions. The tool creates each promotion record, adds Promoted User Story records, then moves on — all in sequence.
  • Separate Promo override — any story can be checked out of its group into its own individual promotion. Each individually keyed as __separate__<storyName>.
  • Re-trigger path (Conflicts Resolved, checkbox unchecked) — no new promotion is created. The existing CR promotion ID is re-used and queued for Merge & Deploy if that option is enabled.
  • Skip checkbox — any eligible story can be skipped for this run without removing it from the verify results. Mutually exclusive with Separate Promo.

Promote Flow — Step by Step

1
Release engineer reviews verify results. Adjusts Separate Promo or Skip checkboxes if needed. Clicks Promote.
2
For each group: create copado__Promotion__c record with source + destination credential and environment IDs (destination credential resolved from an existing promotion in the same pipeline step).
3
For each story in the group: create copado__Promoted_User_Story__c record linking story to the new promotion.
4
If promoting separately from a CR promotion and resolutions are not stale: copy RESOLVED attachments from old promotion to new one (story-specific attachment name match).
5
If Auto Merge & Deploy is checked: call copado__PromoteAction Apex action sequentially per promotion with a 5-second gap between calls (Copado rejects concurrent calls).

Fetch Ready Stories

  • Instead of typing story names manually, one click fetches all eligible stories from the Copado list view — filtered by environment type (QA / UAT) — and pre-fills the input box.
  • The tool also auto-detects the local git repo path from VS Code workspace folders, saving the release engineer from entering it manually on every run.
  • Org alias is auto-populated from .sf/config.json in the workspace — the most recently used org comes up by default with a dropdown history of the last 5 used.

Performance & Architecture

  • All Salesforce queries and git operations run in parallel per story — not sequential. A batch of 10 stories takes roughly the same time as 1-2 stories.
  • No SF CLI plugin loading — the tool connects to Salesforce directly using the @salesforce/core library. No 15-second CLI startup, no plugin overhead.
  • Git repo is cloned once on first use to a temp directory, then only git fetch is run on subsequent runs — no repeated full clones. Branch analysis is performed in-memory with no checkout.
  • 10-minute timeout guards against stuck runs. Debug log panel captures all raw messages from the runner for troubleshooting.
